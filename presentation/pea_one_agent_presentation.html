Chatbot vs Agentic AI: ตารางเปรียบเทียบ 7 มิติ

เติมเต็มช่องว่างจากโจทย์การแข่งขัน: จากระบบตอบคำถาม สู่ปัญญาประดิษฐ์ที่ทำงานแทนลูกค้า
มิติการเปรียบเทียบ Traditional AI Chatbot (ระบบเดิม) PEA One Agent (Agentic AI)
1. ขอบเขตการทำงาน ตอบคำถามตาม Script หรือข้อความที่ฝึกมาเท่านั้น วิเคราะห์ความต้องการ → วางแผนงาน → เรียกเครื่องมือจริง
2. แหล่งข้อมูลที่ใช้ ฐานข้อมูลเดี่ยว หรือ FAQ แบบ Static ข้อมูลไม่อัปเดต ดึงข้อมูลสดจากระบบงาน กฟภ. (OMS / VOC / Knowledge)
3. งานข้ามระบบ ทำไม่ได้ ต้องส่งต่อให้เจ้าหน้าที่มนุษย์ดำเนินการต่อ ประสานงานหลายระบบจบในลูปเดียว (Bounded Agent Loop)
4. ความเสี่ยง Hallucination มักเดาคำตอบ (แต่งเรื่อง) เมื่อไม่พบข้อมูล ก่อผลเสีย Grounded ด้วยเอกสาร กฟภ. เต็มไฟล์ + Fail-Closed ถ้าไม่มีหลักฐาน
5. การเขียนข้อมูล (Write Ops) ปกติทำไม่ได้ หรือทำแบบเสี่ยงโดยไม่มีการกลั่นกรอง 🔒 มนุษย์ต้องยืนยันเสมอ (prepare → confirm → submit)
6. ช่องทางการติดต่อ แยกแชตบอทคนละตัวตามแต่ละแอป ข้อมูลไม่เชื่อมกัน สมองเดียว (Single Brain) บริการทั้ง Web, Voice และ LINE
7. การขยายระบบ (Extensibility) ต้องแก้โค้ดและพัฒนาใหม่ทั้งระบบเมื่อมีระบบใหม่ ⚡ เพิ่มระบบผ่าน Plugin Manifest โดยไม่แตะ Main Agent

หลักการออกแบบ (Design Principles)

ลำดับความสำคัญที่ทีมยึดถือเป็นลายลักษณ์อักษรใน AGENTS.md ตั้งแต่วันแรกของโครงการ
#1
Correctness and safety ความถูกต้องและปลอดภัยสูงสุด — ไม่ยอมแลกกับความเร็ว
หัวใจหลัก
#2
Working MVP ระบบทำงานได้จริงบนเส้นทางหลัก (Critical Path) ที่ผู้ใช้ต้องใช้งาน
#3
Simplicity เรียบง่าย ชัดเจน ไม่สร้างความซับซ้อนที่ยังไม่จำเป็น
#4
Maintainability โค้ดอ่านเข้าใจง่าย มีแบบแผน บำรุงรักษาง่ายในระยะยาว
#5
Test coverage ทดสอบจุดเสี่ยงสูง (Contracts, Write Safety, State Machine)
#6
Architectural purity ไม่ยึดติดกับความสมบูรณ์แบบเชิงทฤษฎีจนลืมคุณค่าทางธุรกิจ
#7
Hypothetical scalability ไม่ออกแบบเผื่อสเกลที่ยังไม่เกิดขึ้นจริงจนเกินความจำเป็น

กฎเหล็กทางสถาปัตยกรรม (Architectural Invariants)

1
Bounded Loop (≤ 12 Steps):

จำกัดลูปการทำงานไม่เกิน 12 ครั้งต่อข้อความ และตัดลูปทันทีหากเรียก Knowledge ซ้ำ เพื่อป้องกันปัญหาโมเดลวนลูปไม่รู้จบ (Infinite Loop Protection)

2
Tool Result is Authoritative:

ผลลัพธ์ที่ได้จาก Tool จริงถือเป็นข้อเท็จจริงสูงสุด โมเดลไม่มีสิทธิ์ปฏิเสธหรือแต่งเรื่องทับผลลัพธ์จากระบบงาน กฟภ.

3
Dynamic Tool Catalogue:

Main Agent ไม่ฮาร์ดโค้ดรายชื่อเครื่องมือ แต่ดึงจาก ToolRegistry.llm_catalogue ทำให้เพิ่มปลั๊กอินใหม่ได้ทันที

4
No Sub-Agents Architecture:

ห้ามแตกเป็น Sub-agent ย่อย เพื่อให้ Audit Trail เป็นเส้นตรงเส้นเดียว ตรวจสอบความถูกต้องได้ง่าย

Write-Safety State Machine: มนุษย์คุมจุดเสี่ยง

ตอบโจทย์ 'มีมนุษย์กำกับดูแลในจุดเสี่ยง' ด้วย State Machine ระดับโค้ด ไม่ใช่แค่ขอร้องใน Prompt
1. LLM เรียกได้

prepare_*

➔
2. รอการตัดสินใจ

pending_confirmation

➔
3. มนุษย์ตัดสินใจ

[Confirm / Reject]

➔
4. Internal Only

submit_*

ยิงบันทึกข้อมูลเข้าระบบงานจริง (OMS / VOC)

🚫 LLM เรียก Submit ไม่ได้

ใน Manifest ทุก submit action ถูกตั้งเป็น exposure: internal โมเดลไม่เห็นชื่อฟังก์ชันนี้ในแค็ตตาล็อก ต่อให้ Prompt Injection ก็สั่งเขียนข้อมูลไม่ได้

🔄 Idempotent Resubmission

หากกดกดยืนยันซ้ำ หรือเครือข่ายส่งซ้ำ ระบบจะคืนผลลัพธ์เดิมทันที ไม่สร้างเคสหรือแจ้งเหตุซ้ำซ้อนในระบบงาน กฟภ.

⚠️ HTTP 409 Conflict Guard

หากพยายามกดยืนยันรายการที่ถูกปฏิเสธไปแล้ว หรืออยู่นอกสถานะ ระบบจะตอบกลับด้วย HTTP 409 Conflict ทันที ไม่ยอมให้ข้อมูลขัดแย้งกัน

💡 ทำไมถึงเหนือกว่า Traditional Chunk RAG?

งานระเบียบและอัตราค่าไฟฟ้า กฟภ. ต้องการความแม่นยำทางกฎหมาย 100% Chunk RAG ทั่วไปมักตัดประโยคเงื่อนไขหลุดบริบท แต่ Long Context อ่านเอกสารทั้งฉบับ ทำให้เข้าใจข้อยกเว้นและตารางอัตราค่าไฟได้อย่างถูกต้องครบถ้วน

🛡️ Fail-Closed: ถ้าไม่มีเอกสาร = บอกว่าไม่รู้

Plugin Manifest: ตัวอย่างจริง (app/plugins/oms/plugin.yaml)

app/plugins/oms/plugin.yaml — Production Manifest YAML Specification 
apiVersion: pea.one/v1
kind: Plugin
metadata:
  id: oms_tool
  name: OMS Outage
  enabled: true
  description: ตรวจเหตุไฟฟ้าขัดข้องด้วยเลขผู้ใช้ไฟ 12 หลัก...
runtime:
  factory: app.plugins.oms.factory:create_plugin
configuration:
  baseUrlEnv: OMS_BASE_URL    # เก็บเฉพาะชื่อ ENV ไม่เก็บ Secret ในไฟล์
  apiKeyEnv: OMS_API_KEY
operations:
  - action: get_outage_by_ca
    exposure: llm              # LLM เรียกอ่านข้อมูลได้
    mode: read
  - action: prepare_outage_with_ca
    exposure: llm              # LLM เรียกร่างรายการได้
    mode: prepare
    submitAction: submit_outage_with_ca
  - action: submit_outage_with_ca
    exposure: internal         # 🔒 บังคับ Internal! LLM ไม่มีสิทธิ์เรียกตรง
    mode: submit

Plugin Loader: 7-Step Fail-Closed Pipeline

Manifest ผิด = ระบบไม่ Start — ดักจับข้อผิดพลาดตั้งแต่ก่อนรันจริงใน app/plugins/loader.py
1
Glob plugin.yaml
อ่านไฟล์ทุกโฟลเดอร์ ปลั๊กอินที่ enabled: false ข้ามไปอย่างปลอดภัย
❌ ไม่พบ / อ่านไม่ได้
2
Model Validate
ตรวจสอบ Schema เบื้องต้นด้วย PluginManifest.model_validate
❌ Schema ผิด
3
Contract Matching
ตรวจ Action เทียบกับ app/contracts.py ต้องมี Pydantic Model รองรับจริง
❌ Action ไร้สัญญา
4
Action Completeness
ตรวจสอบว่าประกาศครบตามที่โค้ดรองรับ ไม่ขาดและไม่เกิน (Missing / Unknown = Error)
❌ สัญญาไม่ตรง
5
Submit Exposure Check
บังคับกฎเหล็ก: ทุก submit action ต้องเป็น exposure: internal เท่านั้น
❌ Submit เปิดให้ LLM
6
Trusted Factory Root
ตรวจว่า Factory Module ต้องอยู่ใต้ app.plugins.* ป้องกันโค้ดแปลกปลอม
❌ Factory นอกพื้นที่
7
Runtime Protocol Check
รัน Factory ตรวจว่ามี execute, reset และชื่อตรงกับ metadata.id
❌ ไม่ครบ Protocol
🛡️ Fail-Closed Principle: หากขั้นตอนใดล้มเหลว ระบบจะปฏิเสธการเริ่มระบบ (Startup Crash) ทันที ป้องกันข้อผิดพลาดหลุดไปถึงผู้ใช้
